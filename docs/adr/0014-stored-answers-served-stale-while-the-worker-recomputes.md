# Analytic pages are stored answers, computed ahead of time and served stale while the worker recomputes them

On the 2-CPU host a Game Plan tab took 40–70 s the first time it was opened after a parse, a Map's Playbook 25–55 s, the team page and v2's overview over a minute (the production log's slow requests, 2026-11-12 to 15): each page cut the Reviews into tallies, replayed the Ratings and built the fixture's Report inside the request, and the Redis cache of a panel (keyed on the parse stamp, kept a week) was empty again after every parse. Staff felt every new Scout as a slow site.

Every analytic page now asks `answers.serve` (`app/services/answers.py`) for its answer, and the answer is a row of `stored_answers`: the page's key (kind, version, parameters, scope), the gzip JSON, and the data stamp it was computed at. The row has no expiry. A read whose stamp still matches is fresh; a read whose stamp moved (a parse, a Review rebuilt, a result, a declared role, a Match or a Veto stored, and for the windowed pages the day) still returns the row at once, marked `X-Answer: stale`, and marks it wanted; only a page with no row at all computes inside the request. The worker's warm-up (`app/services/warmer.py`, one thread at nice 10) keeps the rows current: first what pages have just read stale, then the planned pages with no row (each my team's own pages over every window and Map, and its whole Game Plan against every Team with three parsed Maps, the latest Scouts' fixtures first), then the planned pages that are stale, then any other page opened in the last 30 days. It takes the host's heavy permit for each page and hands it to a parse that waits (`heavy.WAITING`), so it never computes beside a parse. The browser marks a stale body (`_answer`), shows «Шинэчилж байна» in the header, and fetches that query again until it is current.

We chose this over a longer cache TTL or precomputing into Redis because the problem was the first read after every change, not expiry: only computing ahead of time removes it, and only serving the previous answer meanwhile removes the wait while the worker catches up (a full warm-up of ~110 fixtures takes hours on this host). MySQL rather than Redis because the rows must survive a Redis restart and a deploy (Redis there is cstat's, without persistence we control), and a primary-key read of a ~10 KB blob costs a few milliseconds.

## Consequences

- A page can show numbers from before the latest parse for a while; it says so, and Briefings never freeze a stale answer (`lookup(..., fresh=True)`): they 409 on a stamp the page showed, as before.
- What Staff edit by hand (jobs, uploads, the Upcoming match, practice hours, Team goals, a Player's note) stays out of the stored answer and is read on every request by the kind's `live` hook, so an edit never waits for the warm-up.
- A kind's version is in its key: bump it (for the Game Plan, `routers/gameplan.CACHE_VERSION`) when what a page says or its shape changes. An answer of another version is never served, stale or not, and the warm-up prunes it; a deploy that bumps a version is a cold start for that kind until the warm-up reaches it.
- The stored answer of a Workspace with official uploads (or Scrims shown) is its own; the others share the public one, as the old cache did (`scope.cache_part`). The warm-up computes each under its Workspace's scope, and clears a session's memo after a page that let it see Scrims (the veto lab), so they never leak into habits (0010).
- The table is derived and can be emptied at any time; it rides in the nightly dump with the rest (tens of MB).
