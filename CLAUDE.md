# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Workflow: always grill with docs first

Start every new task (feature, design change, plan, or decision) by running the `/grill-with-docs` process before writing any code. Follow-ups inside a task that has already been grilled don't need a new round.

`grill-with-docs` sets `disable-model-invocation: true`, so you cannot call it with the Skill tool. Do what it does instead:

1. Call the Skill tool for `grilling`, then for `domain-modeling`.
2. Run the whole session (questions, recommendations, inline notes) in the user's language. Canonical domain terms such as ADR, CONTEXT.md, bounded context and ubiquitous language can stay in English.
3. Ask each round's questions with the AskUserQuestion tool. Put your recommended answer first and mark it "(Recommended)".
4. Record decisions as you go: terms in `CONTEXT.md`, decisions as ADRs (`domain-modeling` defines the format).

The three skills live in `~/.claude/skills/` and are symlinked into `.claude/skills/`. Claude Code runs here with `CLAUDE_CONFIG_DIR=~/.claude-personal`, which does not load `~/.claude/skills/` on its own; keep the symlinks.

## Commands

The apps run on the host from root `package.json` scripts (npm workspaces). Docker runs only MySQL and Redis. Use npm, not pnpm. Run `nvm use` first: `.nvmrc` pins Node 24, and the shell's default Node 20.14 is too old for Vite 8. Python is managed by uv (`apps/api/.python-version` = 3.13). Every API command goes through `uv run --directory apps/api`, so its cwd is `apps/api`.

- `npm run setup`: `npm install`, `uv sync`, `playwright install chromium`, and copies `apps/api/.env.example` to `.env` if it's missing
- `npm run dev`: starts MySQL and Redis (`docker compose up -d --wait`), then api, worker and public together via concurrently. Run one at a time with `dev:api` (runs migrations first), `dev:worker` or `dev:public`. public: http://localhost:5173, Swagger: http://localhost:8000/docs
- `npm run test:api`. Single test: `npm run test:api -- tests/test_auth.py::test_login_and_me`. The real-demo ingest test is opt-in: `CS_ANALYZE_TEST_DEM=/path/to/x-m1-ancient.dem npm run test:api -- tests/test_real_demo.py`
- `npm run lint`: ruff check and format check (api), oxlint and `tsc -b` (public)
- `npm run workspace:create -- <name>` and `workspace:team -- <workspace> <team>`, then `npm run user:create`, `user:deactivate`, `user:activate`: each prompts for the username, or takes it as `-- <name>` (`create-user` also takes `--workspace`, `--role`, `--player`)
- `npm run db:migration -- "message"` then `npm run db:migrate`. Also `db:up` and `db:down`.
- `npm run openapi`: run after any API schema change (see below)
- `npm run data:rebuild`: cut the Replays, walked routes and callout geometry again from every stored Tick Data bundle (after changing how they are cut, if you'd rather not wait for the lazy rebuild). `npm run data:import [-- folder]` loaded parquet bundles from disk into MySQL during the stateless migration; it stays for any bundle found on disk later.
- `npm run data:cstat [-- ~/gs/cstat]` (`--no-parse` for the rows only): imports cstat's teams, aliases, tournaments, matches and demo rows from its SQLite (read-only; existing rows only get blank fields filled), then parses every map demo cstat still has under `data/maps` that is missing here or stale (or whose Tick Data has no Sightings), in place, never deleting cstat's files (`app/services/cstat_import.py`). Re-runnable; ~10 s a map. `-- --match <hltv id> [--map inferno]` parses just that Match or map.
- `npm run review:fit`: refit the Review's Win probability model on every parsed Round and write `apps/api/app/data/winprob.json` (commit it; docs/adr/0007). `npm run review:rebuild [-- --map <match_map id>]` cuts the Reviews again (they also rebuild lazily when `review.version()` moves).
- `npm run deploy` (Ansible, `ansible/`): builds the public app here and rsyncs the working tree to `/home/cs2.bizon.mn` on cs.bizon.mn (root, `~/.ssh/id_rsa_1`). It refuses a working tree with uncommitted changes (`-e allow_dirty=true` overrides) and a running Scout, which the worker restart would kill (`-e restart_under_scout=true`); the footer shows the deployed commit (`DEPLOYED_COMMIT`). CI (`.github/workflows/ci.yml`) runs ruff and pytest, the migrations up, `alembic check` and down on MySQL 8.4, oxlint, `tsc` and the build, and fails when `npm run openapi` would change the committed contract. Then it runs `uv sync`, migrates, restarts `cs2-api` (uvicorn on 127.0.0.1:8001) and `cs2-worker`, and renders nginx for cs2.bizon.mn (static) and cs2-api.bizon.mn (proxy). MySQL and Redis credentials come from `~/gs/cstat/.env.production`. First time, run `npm run deploy:certs` (Let's Encrypt), and optionally `npm run deploy:db-copy` (local DB to server, refuses a non-empty one without `-e force=true`). On the server, the CLI runs as `cd /home/cs2.bizon.mn/apps/api && uv run python -m app.cli create-user`. Logs: `journalctl -u cs2-worker`. Read `docs/adr/0004-deploy-next-to-cstat.md` first. `npm run deploy:backup [-- -e backup_remote=<rclone remote:path>]` installs the nightly backup (`ansible/backup.yml`, `cs2-backup.timer`): `daily/` everything but `tick_datasets`, `monthly/` the Tick Data whole on the 1st, `ticks/` the Tick Data rows written since the last run; the script's header (`templates/backup.sh.j2`) gives the restore order. Demos are deleted once parsed, so these dumps are the only copy of the Tick Data.
- MySQL and Redis are published on host ports 13306 and 16379 (override with `MYSQL_HOST_PORT` and `REDIS_HOST_PORT`), because 3306 and 6379 are taken by other local containers. `apps/api/.env` points at these ports.
- `dev:worker` uses `--pool=threads`. On macOS, billiard starts prefork children with spawn, which breaks Celery 5.6 tasks (`ValueError` in `fast_trace_task`, celery#9894). Keep the threads pool for local dev. It runs two threads on the `celery` and `light` queues (as production does): Scouts are single-flight on `celery`, and the Review refresh is routed to `light` (`celery_app.task_routes`) so it never waits an hour behind a Scout.
- The root `overrides` forces TypeScript 6 into `openapi-typescript`, whose peer range still says `^5.x`. Codegen works fine with TS 6.

## Architecture

- `apps/api`: FastAPI with **sync** SQLAlchemy 2.0 + Alembic on MySQL (PyMySQL). The API and the Celery worker (`app/celery_app.py`, tasks in `app/tasks.py`) share the same code, models and sessions, which is why the DB layer is sync. Redis DBs: `/0` broker, `/1` results, `/2` app cache (`app/cache.py`).
- `apps/public`: Vite + React + TS, Tailwind v4, TanStack Query via `openapi-react-query`. It calls the API directly at `VITE_API_URL` (CORS, no proxy). The app is dark-only, in cstat's palette: the tokens are CSS variables on `:root` in `src/index.css`, exposed to Tailwind through `@theme inline` (`bg-ground`, `bg-surface`, `bg-surface-2`, `bg-raised`, `text-ink`/`ink-2`/`ink-3`, `border-line`/`line-soft`, `ct`, `t`, `good`, `warn`, `crit`). Use these, not Tailwind's slate/white/sky scales. `replay.css` reads the same variables.
- **Shared schema**: `packages/openapi/openapi.json` is the contract between the apps, and it is committed. `npm run openapi` exports it from the FastAPI app (`app/openapi.py`, no server needed), then generates `apps/public/src/api/schema.d.ts` with openapi-typescript. Commit both files, and never edit them by hand.
- **Auth**: `POST /auth/token` takes an OAuth2 password form, so Swagger's Authorize button works, and returns a 24h JWT. The public app keeps it in localStorage (`src/auth/token.ts`), and a fetch middleware drops it on any 401. Logout is client-only. `get_current_user` reloads the User on every request, which is how deactivation cuts off a still-valid token. Read `docs/adr/0001-jwt-in-localstorage.md` before changing any of this. Failed sign-ins are counted per Username and per address in Redis (`app/services/ratelimit.py`, 10 and 30 per 15 min) and nginx limits `/auth/token` and `/assistant/` per visitor (`CF-Connecting-IP`). Production sets `API_DOCS=false`, which turns off `/docs` and `/openapi.json` (`npm run openapi` still works: it calls `app.openapi()`).
- **Models** (`app/models/`) are ported from the Django project `~/gs/cstat` (`hltv/models/`), in the same layers: `source.py` (HLTV teams, tournaments, matches, demo files), `analysis.py` (what parsing a demo produced: match maps, rounds, events, rollups), `jobs.py` (background analysis runs). Everything is re-exported from `app/models/__init__.py`. Differences from cstat: its `Event` is `Tournament` here, `AnalysisJob.requested_by` points at `users`, and the deprecated `n_matches` is gone. `app/models/base.py` reproduces Django's MySQL column types (BIGINT PKs, UNSIGNED, DOUBLE, DATETIME(6)) with SQLite variants for tests. Choices are `StrEnum`s over plain VARCHAR with no DB check, like Django. `teams.unidentified_name` is a generated column standing in for cstat's partial unique index, which MySQL lacks.
- **Migrations**: one per model layer (0002 source, 0003 analysis, 0004 jobs). After `npm run db:migration`, review the file, then confirm with `uv run --directory apps/api alembic check`. In autogenerated downgrades, delete any `op.drop_index` that comes before an `op.drop_table` of the same table: MySQL refuses to drop an index a foreign key uses, and its DDL isn't transactional, so a failure leaves the schema half-dropped. `Base.metadata` has a naming convention; give multi-column unique constraints explicit short names, because MySQL caps identifiers at 64 characters.
- **Scout jobs** (`/`, `/jobs`, `/jobs/:id` in the public app) port cstat's home and job pages, stopping after parsing: no scouting report yet. `POST /jobs` creates an `AnalysisJob` and `app/services/jobs.enqueue` hands it to Celery, one job at a time (single-flight; the rest wait QUEUED and start when the slot frees). `app/tasks.py` resolves the teams, then goes **match by match**: download, unpack, parse, then delete that match's files before the next (`_process_match`). The stage checklist repeats per match (`set_stage(..., cycle=(n, of))`, shown as «Матч n/N»). A final pass (`_reparse`) re-parses this fixture's maps that are behind `CURRENT_SCHEMA_VERSION` from their stored Tick Data. A map that never parsed and has no Tick Data makes its match download again, and so does a stale map whose Tick Data has no `economy` or `loadout` table (`tickdata.reparseable`, `docs/adr/0003-tick-data-without-economy-means-download-again.md`, `0005`). A Match Map recorded as Demo parts (`…-m2-inferno-p1.dem`, `-p2`; CONTEXT.md) has one Demo row per part (`demos.part`) and is parsed from all of them at once: `tickdata.parse_parts` packs each part, numbers its Rounds by the game's `total_rounds_played` (`demo_parser.round_numbers`) and `tickdata.merge`s the bundles into one Tick Data, the later part winning a Round both hold (`docs/adr/0009`). Only part 1 is listed as pending; parts parsed before the merge download again. An error on one Match fails that Match, not the job. Services: `browser`/`client` (HLTV through Playwright Chromium), `archive` (bsdtar), `store`, `demo_parser` (awpy), `analysis_store` (every analysis table), `tickdata`, `teamnames`. Log text is Mongolian and lives in `app/services/mn.py`.
- **Stateless: everything a parse produces is in MySQL; `data/` is scratch** (`docs/adr/0002-tick-data-in-mysql.md`). A job works under `data/tmp/<job>/` and removes it when it ends; the next job removes any leftovers. Never add code that reads back a file a previous request or job wrote. A map's Tick Data (awpy's parquet dump plus the flash/HE detonation tables and the `economy` table, ~10 MB) is `tick_datasets.bundle`, written by `ingest_map(..., bundle=)` in the ingest's transaction. `app/services/tickdata.py` cuts three things from it at ingest: `geometry` (callout labels, per-floor shares), `walks` (gzip JSON, every route's walks for the movement scene) and the `replay_rounds` rows. They carry `tickdata.derived_version()` (from `REPLAY_SCHEMA`, `WALKS_SCHEMA` and `GEOMETRY_SCHEMA`); bump one when you change how that part is cut, and `tickdata.ensure` rebuilds lazily from the bundle (or run `npm run data:rebuild`). `tickdata.parsed_map(blob)` rebuilds the ingest's `ParsedMap` from a bundle, which is how a stale map is re-parsed with no Demo; it must stay in step with `demo_parser.parse_map` (shared `sides_from_ticks`).
- **HLTV has no API and sits behind Cloudflare.** All reading and downloading happens inside a real Chromium (`channel="chromium"`, not Playwright's headless shell), never through an HTTP client. The constraints in `app/services/browser.py`'s docstring were measured against the live site, so don't "optimize" them away.
- **Two sessions per job run**: `job_db` owns the job row and its story and commits constantly; `db` writes data, and `ingest_map` is one transaction on it. Never pass the data session to `app/services/jobs`, or a progress commit would commit half an ingest. The MySQL engine uses READ COMMITTED (Django's default), and `jobs.check_cancelled` reads the flag on a fresh connection.
- **Live progress**: the worker publishes `{kind, payload}` (`event`/`status`/`activity`) to the Redis pub/sub channel `job.<public_id>` (`app/services/live.py`). `WS /ws/jobs/{public_id}` expects `{"token": ...}` as its first message (close 4401/4404), subscribes, sends a `snapshot`, then relays. The frontend (`src/jobs/useJobLive.ts`) dedupes events by id and falls back to polling `GET /jobs/{id}?after=<last event id>`.
- **STOP is cooperative** (threads pool): it sets `cancel_requested`, which the task checks between items, so a stop lands only after the current download or parse finishes. A job still QUEUED is cancelled right away. If a worker dies mid-job, the row stays RUNNING until the worker starts again: `tasks._recover` (on `worker_ready`) purges the broker queue, fails the orphan and re-sends what was queued (`jobs.recover`).
- **Footer** (`src/system/SystemFooter.tsx`, on every page through `Layout.tsx`): the whole host's CPU, RAM, swap (hidden when there is none), disk (the filesystem under `hltv_data_dir`), load and uptime, plus the worker's light and the Scout it is on, from `GET /system` every 10 s (`app/services/system.py`, psutil). The worker isn't asked with `inspect` (a broadcast that waits out its timeout when nobody answers): it rewrites the Redis key `system:worker` (DB 2) every 10 s with a 30 s TTL and deletes it on shutdown (`tasks._heartbeat`/`_flatline`). CPU % keeps its own baseline per process, because `psutil.cpu_percent(interval=None)` keeps one per thread and reads 0.0 on the API's threadpool.
- **Teams and matches** (`/teams`, `/teams/:id`, `/matches/:id`, `/matches/:id/m/:n`) port cstat's team list, team page (with its "Build a plan" links) and match page, minus position notes and the per-player report. The API lives in `app/routers/teams.py` and `app/routers/matches.py`, and every number comes from stored rows, never from HLTV.
- **Replay**: `app/services/replay.py` (ported, cstat's payload plus each player's Loadout, `REPLAY_SCHEMA` 5) is cut from the Tick Data at ingest, one gzip JSON row per round in `replay_rounds`. The Loadout (Held weapon, items, armor, kit, money at 8 Hz) is the bundle's `loadout` table, read by `demo_parser._loadout`; Tick Data without it still replays (names only under the scoreboard), but like the economy it can't be re-parsed: its Match downloads again (schema 12, `docs/adr/0005-tick-data-without-loadout-means-download-again.md`). `GET .../rounds/{n}` sends the stored bytes with `Content-Encoding: gzip`, and the browser decodes them. Callout labels come from the Tick Data's `geometry`. `apps/public/src/replay/player.ts` is cstat's canvas script ported nearly verbatim. It drives the ids that `Replay.tsx` renders, so keep the two in step. Radar PNGs live in `apps/public/public/radars/` (from cstat's `data/radars`), and `app/services/radar.py` holds Valve's calibration (`pos_x`, `pos_y`, `scale`) plus Nuke's floor split. A map with no shipped PNG still replays, on a dark background.
- **Workspaces** (CONTEXT.md, docs/adr/0011): every User belongs to one Workspace (`app/models/workspace.py`), as Staff or as a Player login tied to a Player (`users.role`, `users.player_id`); a Workspace names its my teams in `workspace_teams`, and `GET /auth/me` returns them, which is how the Scout form and the Game Plan picker start from "we". Every router but `auth` takes `StaffUser` (`app/deps.py`) until the Player pages exist (docs/plans WS-4), and the job socket accepts Staff only. Users exist only through the CLI (`app/cli.py`): `npm run workspace:create -- <name>`, `npm run workspace:team -- <workspace> <team> [--label academy]`, `npm run user:create -- <name> [--workspace W] [--role player --player <steamid>]`; there is no sign-up endpoint. Migration 0009 put every existing User in one Workspace named after the Team most Scouts were run for. Usernames are case-sensitive (`utf8mb4_bin` collation on MySQL). Domain terms are in `CONTEXT.md`.
- **Game plan** (`/gameplan`, `/gameplan/:mine/vs/:theirs[/s/:tab]`) ports cstat's picker and fixture page: 12 tabs, same logic. The analysis services (`mapstrategy`, `roles`, `scouting` (h2h parts), `playerplan`, `gameplan`, `decision`, `charts`, `heatmap_groups`, `movement`, and `mn` copied whole) keep cstat's session-free signatures: the caller binds a session with `with dbctx.using(db):` and the modules call `dbctx.db()`. `dbctx.memo` caches repeated reads (a team's map window, map profiles) on the session for one request. `gameplan.Report` is lazy, so a tab only computes the keys it reads; `app/services/gameplan_view.py` is cstat's `_gameplan_panel` plus its template filters, and returns each panel as worded JSON (`GameplanPanel.data`, typed on the page in `src/gameplan/types.ts`). Panels and the header are cached in Redis DB 2 under `gp:v<CACHE_VERSION>:<mine>:<theirs>:<tab>:<stamp>` (`routers/gameplan.py`; the stamp moves on a parse and on a Review rebuilt, not on a deploy); bump `CACHE_VERSION` when a panel's shape, its SVG or what the code makes it say changes. The Pool's numbers don't depend on the fixture and are shared across requests and processes (`app/services/pool_cache.py`): the role signals (`roles.pool_signals`, which the role baseline and cohorts are cut from) under `pool:roles:v<POOL_SCHEMA>:<hash of the parsed Match Maps>`, read in one pass over the kill and damage feed (`roles._Feed`), and `gameplan.metric_pool` under `pool:metrics:v<METRIC_POOL_SCHEMA>:<parse stamp>`. A missing one is computed under a Redis lock while other processes wait for it (never an older Pool), and the worker warms both after each Match a Scout parses, after `_reparse` and on start (`gameplan.warm_pool`). Bump `POOL_SCHEMA`/`METRIC_POOL_SCHEMA` when a signal or metric changes. Without this, a heavy tab ran 40–80 s and Cloudflare cut it off at 100 s. Class names in the server-drawn SVG and in `gameplan.css` must not collide with Tailwind utilities (`fixed`, `hidden`, `block`, ...): Tailwind styles them on this page. The page warms every other tab in the background, one request at a time, and the nav marks which are ready.
- **Lineups** (CONTEXT.md): each side's up to five Players ride on the page URL as Steam ids (`?mine=…&theirs=…`, API `my_lineup`/`their_lineup` on the header, panel and playbook endpoints), so a Game Plan stays stateless and nothing is stored. `app/services/lineup.py` binds them per request (`lineup.using`, like `dbctx`); the modules' «current five» (`playerplan.current_lineup`, `roles._current_lineup`) read `lineup.names`, which falls back to the latest parsed Match's five. They join the cache key (`lineup.cache_part`). A picked Player who never played for the Team is a newcomer, rated from their last Team (`lineup.elsewhere`). The pickers are `src/gameplan/LineupPicker.tsx`, fed by `GET /gameplan/teams/{id}/players` and `GET /gameplan/players?q=`.
- **Playbook** (the «Юу хийх» tab, `/gameplan/:mine/vs/:theirs/s/todo[/m/:map]`; terms in `CONTEXT.md`): the tab's panel keeps the short action list and adds the Maps in veto order; each Map's Playbook is its own request, `GET /gameplan/{mine}/vs/{theirs}/playbook/{map}`, cached as `gp:v<CACHE_VERSION>:<mine>:<theirs>:playbook:<map>:<stamp>`. `app/services/playbook.py` finds the habits (Setups, stacks, sites, plant timing, rushes, retakes, who is on site at the plant, Set plays, opening duels, economy, matchups, and the same on my team as Self-scout) and returns them structured with their evidence (rounds, Match Maps, Head-to-head count, strength, Replay refs); `mn.playbook_*` words each one with its counter, and `playbook_view.py` assembles the panel. It reads only rows cut at ingest (schema 11): `rounds.ct_buy`/`t_buy` and equipment values, `player_rounds` economy and `primary_weapon`, `round_snapshots` (everyone alive 20 s after freeze end and at the plant), and `grenade_throws.place` (the Callout a grenade landed in, from `tickdata.callouts_at`). Evidence links open `/matches/:id/m/:n?round=N`, which starts the Replay on that round.
- **Levers and Cautions** (CONTEXT.md: Strength, Weakness, Lever, Caution; docs/adr/0008): each Map's Playbook adds «Ашиглах | Анхаарах» per my Side, read from both Teams' Reviews. `app/services/review_pool.py` cuts every Review at the current `review.version()` into tallies (per Match Map, Team and Side: the Summary's numbers, every Finding with its Round, Player, Swing and Spot, each Player's Swing per Round), kept in the process per `review_pool.stamp()`, and judges a Team (or Lineup Player) against the Pool with z ±0.8: the Pool's spread net of chance, the Team's tendency across all its Maps carried to this Map and moved by this Map's own events as far as they allow (`Estimate`; a line carried by the tendency is `all_maps`, and one this Map contradicts says nothing). `app/services/levers.py` pairs facing Sides (`PAIRS`: my Strength × their Weakness first), drops a lone line the other Team's half of its pair takes away (`COUNTERED_Z`), caps Player lines, and adds the data's limits (the maps tab's `map_plan` cautions, Reviews waiting, Sightings, Match Maps without Teams); `mn.advice*` words them (counters in `ADVICE_TEXT`/`ADVICE_PAIR`, my Weaknesses borrow `SUMMARY_ADVICE`). Habit lines tied exactly to a Player or a Callout get a `review` note (`levers.annotate`). The «Юу хийх» list lifts each pick/contest Map's first Lever and Caution after the veto lines, each idea once. The Game Plan never rebuilds a Review: the header asks `review_pool.request_refresh()` (and the worker does on start), which queues `tasks.refresh_reviews` once under a Redis lock; until then stale Reviews are left out and counted. The Assistant reads the same through `gameplan_section` `levers`.
- **Assistant** (CONTEXT.md; the «Ask» button on every page, `src/assistant/`): cstat's chat ported. `app/services/assistant.py` runs Claude (`CLAUDE_MODEL`, default `claude-sonnet-5-5`, server-side refusal fallback) over eight read-only tools backed by the same report builders the pages use (`scouting` findings and matchups, `mapstrategy.build_map_report`, `roles.build_role_report`, `gameplan` sections, the Review and the Summary); it states nothing a tool didn't return. `POST /assistant/chat` streams SSE (`status`, `paragraph`, `audio`, `error`, `done`); the browser resends the earlier turns as plain text, so nothing is stored (the transcript lives in sessionStorage). The page's subject rides along as `context` (a Fixture with its Lineups, a Team or a Match), checked against real rows. Starlette iterates the sync generator from the threadpool with a fresh context per step, so `dbctx.using`/`lineup.using` are bound around each tool call, never across a `yield`. `app/services/voice.py` is ElevenLabs: TTS per paragraph (`eleven_v4_turbo`, the first generation that speaks Mongolian) (made in a background pool so text isn't held back, audio follows as its own event) and `POST /assistant/transcribe` (Scribe, pinned to Mongolian, primed with Map/Team names as keyterms). The keys come from cstat's `.env`; without `CLAUDE_API_KEY` the chat says it isn't configured, without the ElevenLabs pair it is text-only and the mic is hidden.
- **Review** (CONTEXT.md: Review, Swing, Finding; `/matches/:id/m/:n` under the Replay, `src/review/`): `app/services/review.py` cuts one gzip JSON row per Match Map (`match_map_reviews`) from its Tick Data, at ingest (`tickdata.derive`) and lazily when `review.version()` (`REVIEW_SCHEMA`, the Win probability model's version, the Spots' hash) moves. It replays each Round through `winprob` (two logistic models, pre/post plant, committed in `app/data/winprob.json`, docs/adr/0007), credits every kill/plant/defuse's Swing (killer, damage assists by HP up to half, 20% to the flasher who had the victim blind; the victim takes the whole loss), then runs the detectors for Key plays, Mistakes, Missed chances and Utility effects. Blindness is read from the per-tick `flash_duration` and matched to a flash detonation; speed comes from the every-tick positions. Findings are stored as facts and worded on read (`review_view.py`, `mn.review_*`), so changing a sentence needs no rebuild; changing a detector needs `REVIEW_SCHEMA` bumped. The Replay and the Review talk through `ReplayBridge` (`player.ts`): the Review's links call `goto(round, t, sid)`, which rings that player, and the Replay reports the round it shows. The Assistant reads it through its `match_review` tool.
- **Summary** (CONTEXT.md: Summary, Pattern, Focus point): each Team's account of a Round, a Match Map and a Match, from `app/services/review_summary.py` on every read of the stored Review (Findings, buys, kills, plant, Win probability), worded by `mn.summary_*`; nothing is stored, so a threshold or sentence changes with no rebuild. Numbers (openings, trades, full/force/eco buys, pistols, post-plant, retakes, streaks) speak only past fixed thresholds with a fewest count (the 25th/75th percentiles over the 113 Reviews when it was written; half the count with one Side picked), a Pattern is a Finding code at or above its 75th-percentile rate (`PATTERN_P75`), and everything is weighed in Rounds (Swing for Findings, Win probability at the start against the result for numbers) so Focus points rank across kinds. `GET .../review` carries the Map's Summaries (`summary.all|ct|t`) and each Round's (`rounds[].teams`); `GET /matches/{id}/summary` is the Match's (`review_view.match_panel`, Patterns said on two Maps or more), shown on the «Тойм» tab at `/matches/:id`. The match page is wide (`max-w-[1680px]` in `Layout.tsx`): filters (`src/review/filters.ts`, kept in the URL: `team`, `side`, `buy`, `player`, `kind`, `involved`), the Map Summary, then the Replay beside the Round panel from 1440px (`replay.css` lays the Replay out with container queries, not the viewport), then one Players table (scoreboard plus Swing). The filters dim Rounds on the Replay's strip through `data-dim`, never a class: `player.ts` owns that class list. The theme has a colour named `t`, so `border-t` also sets `border-color: var(--t)`; write `border-t-1`.
- **Sightings and aim (schema 13)**: the parse also reads demoparser's `approximate_spotted_by` (32 Hz, only non-empty samples kept) and pitch/scoped/ducking/walking (16 Hz plus every shot) into the Tick Data's `sightings` and `aim` tables. Unlike the economy and the Loadout, Tick Data without them is never downloaded again: its Review skips the four Findings that need them and says so (docs/adr/0006, `tickdata.has_sightings`). Schema 13 does not imply Sightings; check the tables.
- **Spots** (CONTEXT.md): hand-drawn polygons per Map in `apps/api/app/data/spots/<map>.json`, first match wins, filtered by the game Callout and altitude where floors overlap (`app/services/spots.py`). They name places in the Review and label the Replay's callouts toggle (`scene.spots`); Setups, the Playbook and heatmaps stay on Callouts so habits don't split below their Evidence strength.
- **Heatmaps and movement are drawn in the browser.** `GET /gameplan/.../heatmap` returns kill or death coordinates, the callout labels and the overview's world rectangle (`heatmap_groups.points`). `src/gameplan/heatmap.ts` ports cstat's matplotlib picture: the dimmed overview composite, the same gaussian KDE (bandwidth 0.22), inferno/viridis from `colormaps.ts` (generated from matplotlib), dots and labels. `GET .../movement` returns the scene (routes plus the medoid walk per route from the stored walks) and its tables, animated by `src/gameplan/scene.ts`. The API draws no pictures and has no matplotlib.
