# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Workflow: always grill with docs first

Start every new task (feature, design change, plan, or decision) by running the `/grill-with-docs` process before writing any code. Follow-ups inside a task that has already been grilled don't need a new round.

`grill-with-docs` sets `disable-model-invocation: true`, so you cannot call it with the Skill tool. Do what it does instead:

1. Call the Skill tool for `grilling`, then for `domain-modeling`.
2. Run the whole session (questions, recommendations, inline notes) in the user's language. Canonical domain terms such as ADR, CONTEXT.md, bounded context and ubiquitous language can stay in English.
3. Ask each round's questions with the AskUserQuestion tool. Put your recommended answer first and mark it "(Recommended)".
4. Record decisions as you go: terms in `CONTEXT.md`, decisions as ADRs (`domain-modeling` defines the format).

The three skills live in `~/.claude/skills/` and are symlinked into `.claude/skills/`. Claude Code runs here with `CLAUDE_CONFIG_DIR=~/.claude-personal`, which does not load `~/.claude/skills/` on its own; keep the symlinks.

## Commands

The apps run on the host from root `package.json` scripts (npm workspaces). Docker runs only MySQL and Redis. Use npm, not pnpm. Run `nvm use` first: `.nvmrc` pins Node 24, and the shell's default Node 20.14 is too old for Vite 8. Python is managed by uv (`apps/api/.python-version` = 3.13). Every API command goes through `uv run --directory apps/api`, so its cwd is `apps/api`.

- `npm run setup`: `npm install`, `uv sync`, `playwright install chromium`, and copies `apps/api/.env.example` to `.env` if it's missing
- `npm run dev`: starts MySQL and Redis (`docker compose up -d --wait`), then api, worker and public together via concurrently. Run one at a time with `dev:api` (runs migrations first), `dev:worker` or `dev:public`. public: http://localhost:5173, Swagger: http://localhost:8000/docs
- `npm run test:api`. Single test: `npm run test:api -- tests/test_auth.py::test_login_and_me`. The real-demo ingest test is opt-in: `CS_ANALYZE_TEST_DEM=/path/to/x-m1-ancient.dem npm run test:api -- tests/test_real_demo.py`
- `npm run test:public`: Vitest on the public app's pure modules (`*.test.ts` next to them: the Review filters and numbers, Lineups in the URL, the heatmap density, the Assistant's Round tokens). Browser smoke test of the five main paths against a running stack, opt-in: `CS_ANALYZE_SMOKE_WEB=… CS_ANALYZE_SMOKE_API=… CS_ANALYZE_SMOKE_TOKEN=<a Staff JWT> npm run test:api -- tests/test_smoke_e2e.py`. `tests/test_model_quality.py` fails a committed Rating or Win probability that no longer beats its baselines (OPS-9).
- `npm run hltv:canary [-- --team Vitality]`: read one Team on HLTV the Scout's way (search, results, a demo link) and exit 1 naming the selector that broke (`app/services/canary.py`); three HLTV pages, so weekly at most.
- `npm run lint`: ruff check and format check (api), oxlint and `tsc -b` (public)
- `npm run workspace:create -- <name>` and `workspace:team -- <workspace> <team>`, then `npm run user:create`, `user:deactivate`, `user:activate`: each prompts for the username, or takes it as `-- <name>` (`create-user` also takes `--workspace`, `--role`, `--player`)
- `npm run db:migration -- "message"` then `npm run db:migrate`. Also `db:up` and `db:down`.
- `npm run openapi`: run after any API schema change (see below)
- `npm run data:rebuild`: cut the Replays, walked routes and callout geometry again from every stored Tick Data bundle (after changing how they are cut, if you'd rather not wait for the lazy rebuild). `npm run data:import [-- folder]` loaded parquet bundles from disk into MySQL during the stateless migration; it stays for any bundle found on disk later.
- `npm run data:cstat [-- ~/gs/cstat]` (`--no-parse` for the rows only): imports cstat's teams, aliases, tournaments, matches and demo rows from its SQLite (read-only; existing rows only get blank fields filled), then parses every map demo cstat still has under `data/maps` that is missing here or stale (or whose Tick Data has no Sightings), in place, never deleting cstat's files (`app/services/cstat_import.py`). Re-runnable; ~10 s a map. `-- --match <hltv id> [--map inferno]` parses just that Match or map.
- `npm run data:vrs [-- checkout]`: shallow-clones Valve's Regional Standings repo into `data/tmp/vrs` (removed after) and reads every monthly snapshot into `vrs_standings` and every series it counted into `series_results` (`app/services/vrs_import.py`; idempotent, ~45 s). `npm run forecast:backtest` then fits the Rating walk-forward (tune before 2026, score 2026) and writes `apps/api/app/data/rating_params.json` with its scores (commit it).
- `npm run assistant:eval [-- --limit N] [--yes]`: ask the Assistant the 40 questions of `apps/api/app/data/assistant_golden.json` on their pages and score each (a tool it expects called, numbers no tool returned); every question is a paid turn, so without `--yes` it only prints the cost (about $2.40 for all). Answers go to `data/tmp/assistant-eval-*.json` for reading the Mongolian by hand (AS-4).
- `npm run review:fit [-- --since 2026-07-08] [--dry-run]`: refit the Review's Win probability model and write `apps/api/app/data/winprob.json` (commit it; docs/adr/0007). Version 2 is fitted on the states the Review reads from each Match Map's Tick Data (`review.states`, only Tick Data with the economy and the Loadout), and prints v1 against v2 (log loss, Brier, AUC, ECE); the file keeps the calibration by Map, buys and clock under `metrics`. `npm run review:rebuild [-- --map <match_map id>]` cuts the Reviews again (they also rebuild lazily when `review.version()` moves). After a detector changes, rebuild and run `npm run review:thresholds`: it prints each Finding code's 75th-percentile rate per 24 Rounds over the current Reviews, to paste into `review_summary.PATTERN_P75` (and `PATTERN_P75_FROM`).
- `npm run deploy` (Ansible, `ansible/`): builds the public app here and rsyncs the working tree to `/home/cs2.bizon.mn` on cs.bizon.mn (root, `~/.ssh/id_rsa_1`). It refuses a working tree with uncommitted changes (`-e allow_dirty=true` overrides) and a running Scout, which the worker restart would kill (`-e restart_under_scout=true`); the footer shows the deployed commit (`DEPLOYED_COMMIT`). CI (`.github/workflows/ci.yml`) runs ruff and pytest, the migrations up, `alembic check` and down on MySQL 8.4, oxlint, `tsc` and the build, and fails when `npm run openapi` would change the committed contract. Then it runs `uv sync`, migrates, restarts `cs2-api` (uvicorn on 127.0.0.1:8001) and `cs2-worker`, and renders nginx for cs2.bizon.mn (static) and cs2-api.bizon.mn (proxy). MySQL and Redis credentials come from `~/gs/cstat/.env.production`. First time, run `npm run deploy:certs` (Let's Encrypt), and optionally `npm run deploy:db-copy` (local DB to server, refuses a non-empty one without `-e force=true`). On the server, the CLI runs as `cd /home/cs2.bizon.mn/apps/api && uv run python -m app.cli create-user`. Logs: `journalctl -u cs2-worker`. Read `docs/adr/0004-deploy-next-to-cstat.md` first, then `0012` (least privilege): `npm run deploy:db-user` once gives the app its own MySQL account `cs2` (rights on `cs_analyze.*` only; later deploys use it), the worker always has `OOMScoreAdjust=500`, and `-e harden=true` adds the worker's 3500M cap and a read-only filesystem but for `data/`, opt-in until tried on the host. To rotate `JWT_SECRET`, delete `/etc/cs2/jwt_secret` and deploy (everyone signs in again). `npm run deploy:backup [-- -e backup_remote=<rclone remote:path>]` installs the nightly backup (`ansible/backup.yml`, `cs2-backup.timer`): `daily/` everything but `tick_datasets`, `monthly/` the Tick Data whole on the 1st, `ticks/` the Tick Data rows written since the last run; the script's header (`templates/backup.sh.j2`) gives the restore order. Demos are deleted once parsed, so these dumps are the only copy of the Tick Data.
- MySQL and Redis are published on host ports 13306 and 16379 (override with `MYSQL_HOST_PORT` and `REDIS_HOST_PORT`), because 3306 and 6379 are taken by other local containers. `apps/api/.env` points at these ports.
- The worker consumes three queues with a thread each (`-Q celery,parse,light --concurrency=3`): `celery` for Scouts (single-flight), `parse` for parsing that isn't a Scout's (uploads), `light` for the Review refresh. Every parse step, a Scout's included, and `data:rebuild` hold the host's one heavy permit first (`app/services/heavy.py`, a Redis key with a 1 h TTL, cleared on worker start), so two parses never run at once on the small host.
- `dev:worker` uses `--pool=threads`. On macOS, billiard starts prefork children with spawn, which breaks Celery 5.6 tasks (`ValueError` in `fast_trace_task`, celery#9894). Keep the threads pool for local dev. It runs two threads on the `celery` and `light` queues (as production does): Scouts are single-flight on `celery`, and the Review refresh is routed to `light` (`celery_app.task_routes`) so it never waits an hour behind a Scout.
- The root `overrides` forces TypeScript 6 into `openapi-typescript`, whose peer range still says `^5.x`. Codegen works fine with TS 6.

## Architecture

- `apps/api`: FastAPI with **sync** SQLAlchemy 2.0 + Alembic on MySQL (PyMySQL). The API and the Celery worker (`app/celery_app.py`, tasks in `app/tasks.py`) share the same code, models and sessions, which is why the DB layer is sync. Redis DBs: `/0` broker, `/1` results, `/2` app cache (`app/cache.py`).
- `apps/public`: Vite + React + TS, Tailwind v4, TanStack Query via `openapi-react-query`. It calls the API directly at `VITE_API_URL` (CORS, no proxy). The app is dark-only, in cstat's palette: the tokens are CSS variables on `:root` in `src/index.css`, exposed to Tailwind through `@theme inline` (`bg-ground`, `bg-surface`, `bg-surface-2`, `bg-raised`, `text-ink`/`ink-2`/`ink-3`, `border-line`/`line-soft`, `ct`, `t`, `good`, `warn`, `crit`). Use these, not Tailwind's slate/white/sky scales. The Assistant's violet is its own tokens too (`assist`, `assist-2`, `assist-line`, `assist-line-2`; OPS-10), not hex in class names. Printing (GP-7) redefines the tokens under `@media print` in `index.css` (dark ink on white, since browsers drop backgrounds) and hides inputs and buttons; the nav, footer and Assistant carry `print:hidden`, and a Game Plan prints its panel without the tab rail. `replay.css` reads the same variables.
- **Shared schema**: `packages/openapi/openapi.json` is the contract between the apps, and it is committed. `npm run openapi` exports it from the FastAPI app (`app/openapi.py`, no server needed), then generates `apps/public/src/api/schema.d.ts` with openapi-typescript. Commit both files, and never edit them by hand.
- **Auth**: `POST /auth/token` takes an OAuth2 password form, so Swagger's Authorize button works, and returns a 12h JWT. The public app keeps it in localStorage (`src/auth/token.ts`), and a fetch middleware drops it on any 401. Logout is client-only. `get_current_user` reloads the User on every request, which is how deactivation cuts off a still-valid token. Read `docs/adr/0001-jwt-in-localstorage.md` before changing any of this. Failed sign-ins are counted per Username and per address in Redis (`app/services/ratelimit.py`, 10 and 30 per 15 min) and nginx limits `/auth/token` and `/assistant/` per visitor (`CF-Connecting-IP`). Production sets `API_DOCS=false`, which turns off `/docs` and `/openapi.json` (`npm run openapi` still works: it calls `app.openapi()`).
- **Models** (`app/models/`) are ported from the Django project `~/gs/cstat` (`hltv/models/`), in the same layers: `source.py` (HLTV teams, tournaments, matches, demo files), `analysis.py` (what parsing a demo produced: match maps, rounds, events, rollups), `jobs.py` (background analysis runs). Everything is re-exported from `app/models/__init__.py`. Differences from cstat: its `Event` is `Tournament` here, `AnalysisJob.requested_by` points at `users`, and the deprecated `n_matches` is gone. `app/models/base.py` reproduces Django's MySQL column types (BIGINT PKs, UNSIGNED, DOUBLE, DATETIME(6)) with SQLite variants for tests. Choices are `StrEnum`s over plain VARCHAR with no DB check, like Django. `teams.unidentified_name` is a generated column standing in for cstat's partial unique index, which MySQL lacks.
- **Migrations**: one per model layer (0002 source, 0003 analysis, 0004 jobs). After `npm run db:migration`, review the file, then confirm with `uv run --directory apps/api alembic check`. In autogenerated downgrades, delete any `op.drop_index` that comes before an `op.drop_table` of the same table: MySQL refuses to drop an index a foreign key uses, and its DDL isn't transactional, so a failure leaves the schema half-dropped. `Base.metadata` has a naming convention; give multi-column unique constraints explicit short names, because MySQL caps identifiers at 64 characters.
- **Scout jobs** (`/`, `/jobs`, `/jobs/:id` in the public app) port cstat's home and job pages, stopping after parsing: no scouting report yet. `POST /jobs` creates an `AnalysisJob` and `app/services/jobs.enqueue` hands it to Celery, one job at a time (single-flight; the rest wait QUEUED and start when the slot frees). `app/tasks.py` resolves the teams, then goes **match by match**: download, unpack, parse, then delete that match's files before the next (`_process_match`). The stage checklist repeats per match (`set_stage(..., cycle=(n, of))`, shown as «Матч n/N»). A final pass (`_reparse`) re-parses this fixture's maps that are behind `CURRENT_SCHEMA_VERSION` from their stored Tick Data. A map that never parsed and has no Tick Data makes its match download again, and so does a stale map whose Tick Data has no `economy` or `loadout` table (`tickdata.reparseable`, `docs/adr/0003-tick-data-without-economy-means-download-again.md`, `0005`). A Match Map recorded as Demo parts (`…-m2-inferno-p1.dem`, `-p2`; CONTEXT.md) has one Demo row per part (`demos.part`) and is parsed from all of them at once: `tickdata.parse_parts` packs each part, numbers its Rounds by the game's `total_rounds_played` (`demo_parser.round_numbers`) and `tickdata.merge`s the bundles into one Tick Data, the later part winning a Round both hold (`docs/adr/0009`). Only part 1 is listed as pending; parts parsed before the merge download again. An error on one Match fails that Match, not the job. Services: `browser`/`client` (HLTV through Playwright Chromium), `archive` (bsdtar), `store`, `demo_parser` (awpy), `analysis_store` (every analysis table), `tickdata`, `teamnames`. Log text is Mongolian and lives in `app/services/mn.py`.
- **Stateless: everything a parse produces is in MySQL; `data/` is scratch** (`docs/adr/0002-tick-data-in-mysql.md`). A job works under `data/tmp/<job>/` and removes it when it ends; the next job removes any leftovers. Never add code that reads back a file a previous request or job wrote. A map's Tick Data (awpy's parquet dump plus the flash/HE detonation tables and the `economy` table, ~10 MB) is `tick_datasets.bundle`, written by `ingest_map(..., bundle=)` in the ingest's transaction. `app/services/tickdata.py` cuts three things from it at ingest: `geometry` (callout labels, per-floor shares), `walks` (gzip JSON, every route's walks for the movement scene) and the `replay_rounds` rows. They carry `tickdata.derived_version()` (from `REPLAY_SCHEMA`, `WALKS_SCHEMA` and `GEOMETRY_SCHEMA`); bump one when you change how that part is cut, and `tickdata.ensure` rebuilds lazily from the bundle (or run `npm run data:rebuild`). Every bundle is read through `tickdata.load_bundle(dataset)` and written by `tickdata.store` only, so moving them to object storage past OPS-7's threshold (MySQL data 25 GB or the disk 70%; 1.25 GB for 113 Maps on 2026-10-21, 11.2 MB a bundle) touches that module alone. `tickdata.parsed_map(blob)` rebuilds the ingest's `ParsedMap` from a bundle, which is how a stale map is re-parsed with no Demo; it must stay in step with `demo_parser.parse_map` (shared `sides_from_ticks`).
- **HLTV has no API and sits behind Cloudflare.** All reading and downloading happens inside a real Chromium (`channel="chromium"`, not Playwright's headless shell), never through an HTTP client. The constraints in `app/services/browser.py`'s docstring were measured against the live site, so don't "optimize" them away.
- **Two sessions per job run**: `job_db` owns the job row and its story and commits constantly; `db` writes data, and `ingest_map` is one transaction on it. Never pass the data session to `app/services/jobs`, or a progress commit would commit half an ingest. The MySQL engine uses READ COMMITTED (Django's default), and `jobs.check_cancelled` reads the flag on a fresh connection.
- **Live progress**: the worker publishes `{kind, payload}` (`event`/`status`/`activity`) to the Redis pub/sub channel `job.<public_id>` (`app/services/live.py`). `WS /ws/jobs/{public_id}` expects `{"token": ...}` as its first message (close 4401/4404), subscribes, sends a `snapshot`, then relays. The frontend (`src/jobs/useJobLive.ts`) dedupes events by id and falls back to polling `GET /jobs/{id}?after=<last event id>`.
- **STOP is cooperative** (threads pool): it sets `cancel_requested`, which the task checks between items, so a stop lands only after the current download or parse finishes. A job still QUEUED is cancelled right away. If a worker dies mid-job, the row stays RUNNING until the worker starts again: `tasks._recover` (on `worker_ready`) purges the broker queue, fails the orphan and re-sends what was queued (`jobs.recover`).
- **Footer** (`src/system/SystemFooter.tsx`, on every page through `Layout.tsx`): the whole host's CPU, RAM, swap (hidden when there is none), disk (the filesystem under `hltv_data_dir`), load and uptime, plus the worker's light and the Scout it is on, from `GET /system` every 10 s (`app/services/system.py`, psutil). The worker isn't asked with `inspect` (a broadcast that waits out its timeout when nobody answers): it rewrites the Redis key `system:worker` (DB 2) every 10 s with a 30 s TTL and deletes it on shutdown (`tasks._heartbeat`/`_flatline`). CPU % keeps its own baseline per process, because `psutil.cpu_percent(interval=None)` keeps one per thread and reads 0.0 on the API's threadpool.
- **Performance** (OPS-8): every response carries `Server-Timing: app;dur=<ms>` (`app/timing.py`, a plain ASGI middleware so the Assistant's stream is untouched; a request past 10 s is logged as slow). A page never waits on a Review rebuild when only the model or the Spots moved: `review.ensure(..., stale_ok=True)` serves the stored cut marked `stale` (the page says it is being refreshed and polls every 30 s) and asks the worker (`review_pool.request_refresh`); a Review cut by other detectors (`REVIEW_SCHEMA` moved) is still rebuilt inline, since the page may read fields it lacks. The Tick Data's cuts (`tickdata.ensure`) still rebuild inline. In the public app every page but the login, home, jobs, teams list and `/me` loads lazily (`App.tsx`, a skeleton from `ui/Skeleton.tsx` in `Layout`); a fetch middleware stamps each failed response's JSON with its `status` (`api/client.ts`), so `ui/LoadError.tsx` says a 404 is missing and anything else could not be read, with a retry, and queries retry once on a 5xx or no network (`api/errors.ts`), never on a 4xx.
- **Alerts** (OPS-5, `app/services/alerts.py`): an alert is a log line and, with `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` set (deploy reads them from cstat's `.env.production`, else empty), a Telegram message; one key goes out once an hour at most (a Redis key). `python -m app.cli watch`, every 5 minutes on the server (`cs2-watch.timer`), alerts on a missing worker heartbeat, a Scout stage past 45 minutes, the data disk at 85%, and HLTV refusing the browser 3 times in a row (`browser.open` counts them in Redis, a page that gets through resets it). A failed backup or a worker that gave up restarting starts `cs2-alert@<unit>` (OnFailure), the weekly canary (`cs2-canary.timer`, Monday 03:00 in Mongolia) alerts on a broken selector, and a User reaching the Assistant's daily limit alerts once a day. The Jobs page shows the median time per archive downloaded and unpacked, per Map parsed and per Match (`GET /jobs/timings`, from the latest 20 Scouts' stage logs). Error tracking (Sentry) and an outside uptime ping are not set up: both need an account.
- **Teams and matches** (`/teams`, `/teams/:id`, `/matches/:id`, `/matches/:id/m/:n`) port cstat's team list, team page (with its "Build a plan" links) and match page, minus position notes and the per-player report. **Players** (`/players/:steamid`, `GET /players/{steamid}`, `app/services/player_page.py`; PL-10's pressure Rounds and consistency in `app/services/pressure.py`: Swing per Round on pistols, match points in regulation and close finishes (Round 19 on, within one) beside every Player's, and the spread of per-Map Swing per Round placed among Players with five Maps or more): one Player's teams, form Match Map by Match Map (Swing per Round from the stored Reviews through `review_pool.data()`, with a 5-map rolling mean), numbers by Map and Side, Findings per 24 Rounds against every reviewed Player's, Callouts 20 s in, and guns; team-page chips and the Review's player card link to it. `/compare?a=<steamid>&b=<steamid>` (PL-9, from the Player page) sets two Players' numbers side by side, a tryout against the Player whose spot they would take, from the same `GET /players/{steamid}` answers. Steam ids are strings in JSON and in the path (they exceed JavaScript's safe integers); `review.CODE_KIND` maps each Finding code to its kind. The API lives in `app/routers/teams.py` and `app/routers/matches.py`, and every number comes from stored rows, never from HLTV.
- **Replay**: `app/services/replay.py` (ported, cstat's payload plus each player's Loadout and, schema 6, who had which enemy in sight as `sights` stretches, `REPLAY_SCHEMA` 8 (7: the Round search's `tokens`, VIZ-7; 8: `steps`, every footstep others could hear from the Tick Data's `footsteps`, drawn as widening rings in the walker's Side colour behind the Replay's «footsteps» toggle, VIZ-12); the Replay's «vision» toggle draws each living Player's 90° cone and, with Sightings, a dashed line to every enemy in sight, VIZ-4) is cut from the Tick Data at ingest, one gzip JSON row per round in `replay_rounds`. The Loadout (Held weapon, items, armor, kit, money at 8 Hz) is the bundle's `loadout` table, read by `demo_parser._loadout`; Tick Data without it still replays (names only under the scoreboard), but like the economy it can't be re-parsed: its Match downloads again (schema 12, `docs/adr/0005-tick-data-without-loadout-means-download-again.md`). `GET .../rounds/{n}` sends the stored bytes with `Content-Encoding: gzip`, and the browser decodes them. Callout labels come from the Tick Data's `geometry`. `apps/public/src/replay/player.ts` is cstat's canvas script ported nearly verbatim, with a camera added (VIZ-3: wheel or pinch zooms around the pointer up to 6x, drag pans, Shift-click a Player to follow him, double-click resets; on a phone a tap plays or pauses and a swipe seeks). The match page's «клип» button records ten seconds of the Replay from the moment shown as a WebM in the browser (VIZ-13, `ReplayBridge.record`, `canvas.captureStream` + `MediaRecorder`; nothing goes to the server) and downloads it. With Sightings, the scrub bar marks the Round's first contact (the earliest sight stretch, `motion.firstContact`; a triangle with who saw whom). Its arithmetic (a Player between two frames, headings, the last weapon fired, blindness, the camera's zoom and world points) is `replay/motion.ts`, tested with Vitest (VIZ-1); new pure logic goes there rather than into the closure. It drives the ids that `Replay.tsx` renders, so keep the two in step. Radar PNGs live in `apps/public/public/radars/` (from cstat's `data/radars`), and `app/services/radar.py` holds Valve's calibration (`pos_x`, `pos_y`, `scale`) plus Nuke's floor split. A map with no shipped PNG still replays, on a dark background.
- **Workspaces** (CONTEXT.md, docs/adr/0011): every User belongs to one Workspace (`app/models/workspace.py`), as Staff or as a Player login tied to a Player (`users.role`, `users.player_id`); a Workspace names its my teams in `workspace_teams`, and `GET /auth/me` returns them, which is how the Scout form and the Game Plan picker start from "we". Staff routers take `StaffUser` (`app/deps.py`), and the job socket accepts Staff only. A Player login (docs/plans WS-4) lands on `/me` (`GET /me/overview`, `app/services/me.py`: its last ten Match Maps and Scrims, and its Focus points from the stored Reviews of the last five, worst Swing first, with what to keep doing); it opens the match pages of Matches it played (`deps.can_see_match`) and its own `/players/:steamid`, nothing else. On a side-wide Finding (`advantage_lost`) a Player carries only their own death's Swing; `time_out` and `kitless` stay the Team's. The first Staff of a Workspace comes from the CLI (`app/cli.py`): `npm run workspace:create -- <name>`, `npm run workspace:team -- <workspace> <team> [--label academy]`, `npm run user:create -- <name> [--workspace W] [--role player --player <steamid>]`. Everyone after is invited from `/workspace` (`app/services/members.py`, `app/routers/workspace.py`, docs/plans WS-3): a one-time link valid 7 days (only its SHA-256 is stored, `invites`), opened at `/invite/:token` before any sign-in, makes a Staff or a Player login; the same kind of link with `user_id` resets a forgotten password. Staff deactivate and reactivate members and tie a Player login to its Player, never themselves out, and a Workspace always keeps an active Staff. There is no open sign-up. Passwords are 10 characters or more. Migration 0009 put every existing User in one Workspace named after the Team most Scouts were run for. Usernames are case-sensitive (`utf8mb4_bin` collation on MySQL). Domain terms are in `CONTEXT.md`.
- **Audit log** (WS-7, `app/models/audit.py`, `app/services/audit_log.py`, `GET /workspace/audit`, on the Workspace page): `audit_log.record(db, actor, action, subject, **detail)` adds a line in the action's own transaction for each change to who can see or do what: a member's role or access (also from the CLI, actor "server"), an invite made, revoked or used, a Briefing shared or deleted, a Strat or Playlist deleted. Never a secret in `detail` (no invite token, password or key). Migration 0024.
- **Practice week** (RV-11, `/week` in the Staff nav, `GET /workspace/week`, `app/services/practice_week.py`): the research's tier-2 week (Monday review, Tuesday–Wednesday Scrims, Thursday prep, Friday match, Saturday Scrim and the next opponent, Sunday rest), each day filled from what the Workspace has: the my team's latest official Matches to review (their agenda), the active Development goals with where each stands, the latest Scrims' Focus points as this week's Scrim goals, and the latest Briefings' fixtures (Game Plan, veto lab). - **Game plan** (`/gameplan`, `/gameplan/:mine/vs/:theirs[/s/:tab]`) ports cstat's picker and fixture page: 12 tabs, same logic. Playlists (`/playlists`) are ordered Rounds with a line each; a shared one opens its Matches to the Workspace's Player logins (`deps.can_see_match`).
- **Development plans** (CONTEXT.md: Development plan; docs/plans RV-9; `app/services/development.py`, `app/routers/development.py`): `development_goals` holds a Player's goals per Workspace: a KPI (a Finding code per 24 Rounds, or opening duels won, deaths traded, KAST, ADR; `development.kpis()`), its baseline (the last 90 days when not given), target and dates. Progress is measured since the goal started from his Match Maps and Scrims (his own development, docs/adr/0010; `scope.allow_scrims`), with an 80% range from resampling whole Match Maps, and read as reached (the range's worse end past the target), close or not yet. Suggestions are his Mistakes and Missed chances past PL-7's test (Beta prior per code, lfsr < 0.10, 1.2× every Player's rate), ranked by the Findings a goal at the Pool's rate would save. Staff edit plans on the Player page; a Player reads his own on `/me`.
- **Review** (CONTEXT.md: Review, Swing, Finding; `/matches/:id/m/:n` under the Replay, `src/review/`): `app/services/review.py` cuts one gzip JSON row per Match Map (`match_map_reviews`) from its Tick Data, at ingest (`tickdata.derive`) and lazily when `review.version()` (`REVIEW_SCHEMA` and the Win probability model's version) moves or the Map's own Spots file does (`spots_version`, `spots.version(map)`, VIZ-11: editing one Map's Spots rebuilds that Map's Reviews only; `review.current`). It replays each Round through `winprob` (two logistic models, pre/post plant, committed in `app/data/winprob.json`, docs/adr/0007; version 2 also reads the living's average health, the grenades they carry, which side made the last kill, after the plant the defuse race and before it the pair of buys, RV-4), credits every kill/plant/defuse's Swing (killer, damage assists by HP up to half, 20% to the flasher who had the victim blind 1 s or more; the victim takes the whole loss, a teamkiller alone his teamkill; a plant is charged to the CTs alive, a defuse to the Ts alive), settles the rest (`_RoundReview.settle`, Swing v2, RV-2: Trades' 20% shares, then whatever the events left unassigned, so each Team's Players add up to exactly its Win probability's move over the Round), then runs the detectors for Key plays, Mistakes, Missed chances and Utility effects. Blindness is read from the per-tick `flash_duration` and matched to a flash detonation; speed comes from the every-tick positions. Findings are stored as facts and worded on read (`review_view.py`, `mn.review_*`), so changing a sentence needs no rebuild; changing a detector needs `REVIEW_SCHEMA` bumped (8 since RV-12: a T who stands 1,400+ units from every living teammate 30 s into 40% of their 6+ T Rounds lurks, `review._lurkers`, and a lurker's lone death is not `untraded`; a bomb site is the median of the Map's stored plants, `review._sites`, and the timing Findings read it: `late_execute`, the Ts first on a site with under 20 s left, not outnumbered, lost, and `early_rotate`, a CT who left the site 5–20 s before the Ts hit it and planted). The Replay and the Review talk through `ReplayBridge` (`player.ts`): the Review's links call `goto(round, t, sid)`, which rings that player, the Replay reports the round it shows (`onRound`) and its clock a few times a second (`onTime`, VIZ-6: the Win probability chart's cursor follows it, and a click on the chart goes to that second). A link to a moment is `/matches/:id/m/:n?round=R&t=T[&player=<steamid>]` (VIZ-2): the page goes there paused once the Replay is up, and «Энэ агшны холбоос хуулах» copies the one on the canvas. The Assistant reads it through its `match_review` tool.
- **Summary** (CONTEXT.md: Summary, Pattern, Focus point): each Team's account of a Round, a Match Map and a Match, from `app/services/review_summary.py` on every read of the stored Review (Findings, buys, kills, plant, Win probability), worded by `mn.summary_*`; nothing is stored, so a threshold or sentence changes with no rebuild. Numbers (openings, trades, full/force/eco buys, pistols, post-plant, retakes, streaks) speak only past fixed thresholds with a fewest count (the 25th/75th percentiles over the 113 Reviews when it was written; half the count with one Side picked), a Pattern is a Finding code at or above its 75th-percentile rate (`PATTERN_P75`), and everything is weighed in Rounds (Swing for Findings, Win probability at the start against the result for numbers) so Focus points rank across kinds. `GET .../review` carries the Map's Summaries (`summary.all|ct|t`) and each Round's (`rounds[].teams`); `GET /matches/{id}/summary` is the Match's (`review_view.match_panel`, Patterns said on two Maps or more), shown on the «Тойм» tab at `/matches/:id`. The match page is wide (`max-w-[1680px]` in `Layout.tsx`): filters (`src/review/filters.ts`, kept in the URL: `team`, `side`, `buy`, `player`, `kind`, `involved`), the Map Summary, then the Replay beside the Round panel from 1440px (`replay.css` lays the Replay out with container queries, not the viewport), then one Players table (scoreboard plus Swing). The filters dim Rounds on the Replay's strip through `data-dim`, never a class: `player.ts` owns that class list. The theme has a colour named `t`, so `border-t` also sets `border-color: var(--t)`; write `border-t-1`.
- **What a Review can't show**: Tick Data without Sightings skips `review.SIGHT_CODES`, without a Loadout `review.LOADOUT_CODES`; the payload lists them (`needs_sightings`, `needs_loadout`), the page says so, and the Pool counts a code's rate only over Team-maps that could show it (`review_pool.can_show`). A Finding without Swing is still worth `review_summary.ZERO_SWING_VALUE` Rounds in the Summary and the Pool (`review_summary.value`; a lost save by the Team's next buy).
- **Sightings and aim (schema 13)**: the parse also reads demoparser's `approximate_spotted_by` (32 Hz, only non-empty samples kept) and pitch/scoped/ducking/walking (16 Hz plus every shot) into the Tick Data's `sightings` and `aim` tables. Unlike the economy and the Loadout, Tick Data without them is never downloaded again: its Review skips the four Findings that need them and says so (docs/adr/0006, `tickdata.has_sightings`). Schema 13 does not imply Sightings; check the tables.
- **Parse events (schema 14, DATA-5)**: the parse also reads, in one pass over `grenade_thrown`, `item_pickup` and `player_ping` (0.3 s a map), the game rules' timeout flags once a second over each freeze time, and the scoreboard's per-round numbers (`*_this_round`) as each round's post-round ends, into the Tick Data's `throws`, `pickups`, `pings`, `timeouts` and `round_stats` (`tickdata.EVENT_TABLES`, optional like the Sightings: `tickdata.has_events`), plus `in_site`/`defusing` on the aim grid. They fill `rounds.ct_timeout`/`t_timeout`/`tech_timeout` (the flags follow the Side, not the Team) and `player_rounds.enemies_flashed`/`utility_damage`/`money_saved`/`kill_reward`; from older Tick Data these stay None. Recorded GOTV demos carry no `bomb_beginplant`/`bomb_begindefuse`, and `grenade_thrown` misses about 40% of throws, so each grenade's throw (`grenade_throws.thrown_*`: tick, where the thrower stood, yaw, pitch, Callout) comes from the first point of awpy's projectile trajectory (`demo_parser.projectile_starts`, in every bundle) matched to the grenade, with the thrower's tick there: it fills on any re-parse. `throw_tick` and `thrower_*` stay what they were (a flash's or HE's pop, and where the thrower stood then), which the Replay draws.
- **Aim** (PL-5, `app/services/aim.py`): the Review counts each Player's clean engagements on a Map with Sightings (a stretch of Sighting of a living enemy, gun in hand, not blind: `_RoundReview.engagements`, stored as `players[].aim`) and the Pool keeps them per Match Map (`review_pool.Data.aims`). The Player page gives, past 100 engagements, the median time to damage (within 1 s), the median crosshair angle off the enemy's head as he came into view, the counter-strafed share of shots (below the weapon class's moving share) and the first shots that hit, each as a percentile among every Player past 100. The Sighting is the radar's approximation, which spots late, so the numbers rank Players against each other and are not Leetify's scale; smoke is not ruled out.
- **Map pool** (TM-6, `app/services/map_pool.py`, on the Team page): the Active Duty Maps are Valve's on the day, from `app/data/patches.json` (`map_pool.active_duty`; only when the file names fewer than seven, the seven played most in the 90 days before the latest official Match, three times or more, topped up from the file's), and the Forecast's veto, the Game Plan's map board and the pool's "untested" read that list. Each Map's strength is the share of Rounds won pulled toward the Team's own share by one Map's worth (24 Rounds); the pool's depth counts Active Maps played twice or more and no more than 5 points under its own share. Veto history needs HLTV's match pages (DATA-3), not read yet.
- **Patch eras** (DATA-7, `app/services/patches.py`): `app/data/patches.json` lists the CS2 patches that change how Rounds play (date, name, note) and each Map's Active Duty periods, from Valve's notes (docs/plans/12 section 5); edit it by hand and commit. A Match Map belongs to the latest patch on or before its day (`patches.era`, computed on read, so nothing is stored per Map): the match page names it, `GET /patches` lists them with today's pool, the Playbook takes `since=<day>` (a chip for the latest patch) and, since GP-9's last part, `score=ahead|close|behind` (the Team's lead before the Round within its Match Map, 2 Rounds either way, `playbook._leads`), and `review:fit --since <day>` fits the Win probability on one era (`--dry-run` to compare without writing; on 2026-10-21 the Cache/C4 era's 65 Maps fitted no better than all 75, so the model stays on all).
- **Data coverage** (DATA-9, `/data`, linked from the footer; `GET /data/coverage`, `app/services/coverage.py`): each Team's parsed Match Maps by Map and how many lack something (behind the parse schema, no Tick Data, no Loadout so the Match downloads again, no Sightings, no schema 14 events, stale cuts, stale Review), its last Match and parse, the Workspace's Teams first; each Map's Pool (Match Maps, Teams); and the download-again queue (behind and not reparseable from its Tick Data), the same rule `tasks` follows.
- **Momentum** (TM-11, `app/services/momentum.py`, `GET /data/momentum`, on `/data`): on the Pool only, the Round after a streak of three or more won against what the two buys expected on that Side (the Pool's buy-pair rate pulled toward 50% by 10 pseudo-Rounds), split by streak length and by the other Team's timeout in the freeze time; the residual has an 80% Wilson range. Team strength is not adjusted, and no Team is ever said to tilt. On 2026-10-21: 791 Rounds, +6.6 points (+4.5…+8.8), and none after a timeout (−0.9).
- **Playbook views** (GP-9): `?buy=full|light` and `?days=30|90|180` on the Playbook (and its URL) read the habits over the opponent's and our Rounds of that buy or that recent only (`playbook._viewed`); the economy, pistols and conversion keep every Round, which they need for what comes next. The view joins the cache key and the panel says how many Rounds it read (`view`).
- **Forecast: why, and "X in for Y"** (FC-6, FC-9): the Forecast says what it rests on (`forecast.why`: the Ratings' gap and each Team's Rating move over 60 days, worded by `mn.forecast_why`, on the decision tab). A Lineup that keeps three or more of the five a Team's results were won with now moves its Rating a fifth of the way toward each newcomer's last Team's Rating (`Standing.swapped`/`swap_shift`, limit `swap`); fewer than three kept still rates the Lineup by its Players alone.
- **Veto lab** (GP-10, `/gameplan/:mine/vs/:theirs/veto`, `POST /gameplan/{mine}/vs/{theirs}/veto`, `app/services/veto_lab.py`): the veto played step by step, every choice in the URL. Each Map's chance starts at the Forecast's (one chance for every Map, since map offsets hurt its walk-forward check) and Staff move it by hand (±25 points), beside each side's map pool strength and our Scrims on that Map (ours only, docs/adr/0010). `forecast.veto_from` plays it from where it stands: our series chance now (expected and minimax), every option at the next step valued, their likely choice at theirs, the line from there. Veto history waits for DATA-3.
- **Map sheet** (GP-3, `/gameplan/:mine/vs/:theirs/sheet/:map`, `src/pages/MapSheetPage.tsx`, linked from each Map's Playbook header): one Map on one page for paper or a phone, built from the Playbook, the timeout card and the style: each section cut to its two or three strongest lines, each line with its Evidence strength, the Map's cautions at the foot. It opens with the break between Maps (GP-4, `GET /gameplan/{mine}/vs/{theirs}/between?played=`, `app/services/between.py`, `gameplan/Between.tsx`): what the opponent did differently on a Map they just played (their newest reviewed by default) against their other Maps, from review_pool's tallies: per Side the openings and trades won, post-plant, retakes and how often they forced, the Findings they made more of, and who was hot or cold, each said only past a 90% chance it is not luck; sites are left out, as they don't carry to the next Map.
- **Timeout card** (GP-4, `app/services/timeout_card.py`, `GET /gameplan/{mine}/vs/{theirs}/timeout/{map}`, under each Map's Playbook, prints): the opponent's Rounds on the Map right after they lost two in a row or called a timeout ("under pressure") against the rest, on the Playbook's signals (site, rush, stack, early pick, force); a move is said at 15 points or more on four Rounds or more and when it is likely real (`stats.chance_higher` past 0.85), with our answer (`mn.TIMEOUT_SIGNALS`); the Pool's next Round after a losing run, with and without a timeout, comes with it.
- **Style** (TM-5, `app/services/style.py`): a Team's numbers on a Map, Side by Side, each as its percentile among every Team with 12+ Rounds on that Side of the Map: on T when the first duel comes and the bomb goes down, plants inside 40 s and after 70 s, executes (2+ smokes or fires landing on the plant site in the 15 s before it) and fakes; on CT early picks, delaying utility in the first 25 s and saves after a lost plant; on both a force after a lost pistol, the Round won after the first kill or death, full buys against light ones. The Pool is computed once per parse and Map (`pool_cache`, `style:v<STYLE_SCHEMA>:<map>:<parse stamp>`; bump `STYLE_SCHEMA` when a number changes). On the Team page (`GET /teams/{id}/style[?map=]`) and folded under each Map's Playbook for both Teams (`GET /gameplan/{mine}/vs/{theirs}/style/{map}`, `src/team/Style.tsx`). Since `STYLE_SCHEMA` 2 it also reads the Round search's tokens: a Side in mid at 20 s, a T lurk (one away from three or more on the other site at 30 s), and how many seconds another CT takes to reach a site after its opening there was lost (within 20 s); Callouts lean to a site as `after_contact.place_leans` says.
- **After the first contact** (TM-7, `app/services/after_contact.py`, `GET /teams/{id}/after-contact?map=`, on the Team page): each Round's opening (first kill) is placed A, mid or B by where the victim fell (`playbook.lean`), and branches into where the bomb went down (A, B, none) with the Rounds won and Replay refs (⧉ opens them in ghost mode). T also gets where most of them stood at the Setup and whether they planted the other site (a rotate), plant timing (median, after 60 s), and where they sat at the plant; CT, having lost the opening at a site, whether another CT reached that site's Callouts within 10 s (the Round search's tokens; a Callout's lean is where the deaths in it fell, `place_leans`), and retakes by the numbers alive at the plant (ahead, even, behind).
- **Roster timeline** (TM-10, `app/services/roster.py`, `GET /teams/{id}/roster`, on the Team page): each Player's Match Maps for the Team cut into stretches wherever 45 days pass without one, newest Players on top, drawn as one-hue bars over months (`src/team/Roster.tsx`).
- **Eco-adjusted duels** (PL-6, `app/services/duels.py`): every kill between enemies is a duel; each Player's class is what he bought for the Round (`player_rounds.primary_weapon`: sniper, rifle, rifle2, smg, or pistol when he bought no gun). The Pool's chance for each pair of classes by the killer's Side (`duels.table`, shrunk toward the pair over both Sides, memoised per request) makes a Player's duels worth what they beat: the Player page says his duels won against what the guns expected, per Round, and his Swing per Round by the opponent's Rating tier now (`team_strength.ranks`/`tier_of`).
- **Timeout audit and opening duels** (RV-8, `app/services/audit.py`, `GET /matches/{id}/maps/{n}/audit`, `src/review/Audit.tsx` under the match page's Players): each timeout with the Rounds its Team had lost in a row before it and the Round after against its buys' Win probability; a Team that lost three in a row in regulation with a timeout left and no break (half, overtime half, either side's timeout) is marked as having gone without one; `audit.pool()` sets the next Round after such a run with and without a timeout over every Match Map whose timeouts are known (schema 14). Opening duels per Player: taken, won, his first deaths traded, his Team's 5v4 and 4v5 won (also on the Player page).
- **A new Map in the pool**: follow `docs/new-map.md` (VIZ-11): the pool's dates, the radar image, the calibration, the Spots, the Win probability refit.
- **Spots** (CONTEXT.md): hand-drawn polygons per Map in `apps/api/app/data/spots/<map>.json`, first match wins, filtered by the game Callout and altitude where floors overlap (`app/services/spots.py`). They name places in the Review and label the Replay's callouts toggle (`scene.spots`); Setups, the Playbook and heatmaps stay on Callouts so habits don't split below their Evidence strength.
- **Coach drawings** (VIZ-8): Staff draw on the Replay from the Round's notes box (arrow, circle, a word), in world units, and the strokes are saved with the Note (`review_notes.drawing`, JSON, up to 12; a Note may be only a drawing). The Replay asks the page for the pen and the marks through `ReplayBridge.pen`/`onShape`/`shapes` (`RoundNotes` hands them up with `onPens`), shows a Note's marks in its Round within 4 s of its moment (always, when it has none), and `bridge.redraw` repaints a paused canvas when they change. With a pen picked, a drag draws instead of panning.
- **Round search** (VIZ-7, `/search`, `app/services/round_search.py`, `POST /search/rounds`, `GET /search/places/{map}`): each stored Replay Round also keeps, second by second, how many of each Side's living Players stood in each Callout (`replay_rounds.tokens`, gzip JSON cut with the Replay, `replay.tokens`, REPLAY_SCHEMA 7; ggViz's state tokens). A search names a Map, the Side, optionally its Team, buy and score (that Side's Team 2+ ahead, within 1, or 2+ behind when the Round began, `round_search._leads`, VIZ-5), and up to six conditions (a Callout, a fewest and most of that Side there, a window of seconds after freeze end, ±2 s); a Round matches when every condition holds at some second of its window (so a "most" says "at some moment no more than", not "throughout"). The results say how often that Side won them, open in ghost mode, and with `heat` (deaths or kills) come with a heatmap of where that Side died or got its kills in all of them (`round_search._heat`, drawn by `gameplan/heatmap.ts`). Rounds cut before schema 7 have no tokens until the Tick Data is rebuilt (`npm run data:rebuild`, or lazily as their Replay is opened).
- **Ghost mode** (VIZ-5, `/ghost?r=match.map.round,...[&side=t][&team=Name]`, `src/pages/GhostPage.tsx`): up to 30 stored Replay Rounds of one Map played over each other from freeze end, every Player a faint dot with a 3 s trail, by Side or Team; each Playbook line with two or more Rounds links its «⧉ давхар». It reads the same `replay_rounds` the Replay does and draws on its own canvas, not through `player.ts`.
- **Heatmaps and movement are drawn in the browser.** `GET /gameplan/.../heatmap` returns kill or death coordinates, or (VIZ-9 `kind=positions`) where the Team's living Players stood 20 s in (the Setup snapshots), optionally kept to one game Callout (`place`, the grid's «Газар» row: "where on B do they die"; each answer lists the Callouts it has), the callout labels and the overview's world rectangle (`heatmap_groups.points`), narrowed by `phase` (0–15, 15–30, 30–60, 60+ seconds, or after the plant) and `buy` (full, light) and, with `compare`, a sample of every other Team's on the Map the same way, drawn as where this Team is more (red) or less (blue) than usual (VIZ-9). The heatmap and movement tabs keep their view in the page URL (`gm` Map, `gt` Team, `gp` Player, `gs` Side, `gl` floor, `gph` phase, `gb` buy, `gc` compare; g-prefixed because the Lineups use `mine`/`theirs`), checked against the grid's index on load (VIZ-2). `src/gameplan/heatmap.ts` ports cstat's matplotlib picture: the dimmed overview composite, the same gaussian KDE (bandwidth 0.22), inferno/viridis from `colormaps.ts` (generated from matplotlib), dots and labels. `GET .../movement` returns the scene (routes plus the medoid walk per route from the stored walks) and its tables, animated by `src/gameplan/scene.ts`. The API draws no pictures and has no matplotlib.
